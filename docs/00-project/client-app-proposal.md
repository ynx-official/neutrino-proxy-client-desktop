## 1. 结论与改动规模

建议按已选定路线，新增 `neutrino-proxy-client-app`：Rust + Tokio 实现通信内核，Tauri 2 提供桌面宿主和托盘，Vue 3 + JavaScript 提供配置与状态界面。用户安装后不需要另装 Java、执行启动命令或手工编辑 YAML。

这是中等偏大的客户端重写。现有客户端有 26 个 Java 源文件、2,075 个物理行（包含注释和空行，2026-10-15 本地统计），另外使用 `neutrino-proxy-core` 中的协议类。代码体量可控，但需要重新证明网络行为、配置迁移、资源回收和跨平台分发可靠。不能以现有行数等比例推算 Rust 代码量或交付时间。

界面采用已确认的 Airtable 风格，分为连接、日志、设置三页。可直接查看[已连接主页样图](../02-design/assets/client-app-connected.png)和[首次配置样图](../02-design/assets/client-app-connection-setup.png)，完整交互规则见[界面设计](../02-design/client-app-ui.md)。

| 工作项 | 改动程度 | 原因 |
|---|---|---|
| 协议编解码、认证和心跳 | 中 | 线上的字节格式保留，实现语言和调度方式变化 |
| TCP 双向转发、隧道复用、流量背压 | 大 | 重写连接生命周期和缓冲区管理，慢连接不能拖垮内存 |
| UDP 会话、傀儡端口、响应次数与超时 | 大 | 包含会话路由和资源复用，需要覆盖边界行为 |
| TLS 与 JKS 导入 | 中到大 | Java 证书加载方式不能直接搬到 Rust，证书验证行为需要单独核对 |
| 配置兼容和客户端身份迁移 | 中 | 保留字段含义、默认值及已有身份，处理旧参数与新运行时差异 |
| 桌面界面、托盘与本地日志 | 中 | 页面数量少，但需要正确呈现后台状态并独立管理窗口生命周期 |
| Windows / macOS 安装和长期运行验证 | 大 | 两个平台分别验证，不能由单机编译成功替代 |

主要成本在通信内核和验证。只完成“能够认证并连接”是早期里程碑，不能代表已经替代原客户端。

## 2. 已确认的产品需求

- 服务对象：在 Windows 或 macOS 电脑上连接现有 Neutrino Proxy 服务的用户。
- 核心问题：命令、运行环境和分散配置增加使用成本；需要一个能长期挂后台的本机连接工具。
- 首版功能：配置服务器、License、SSL；连接、断开、重连、连接状态和日志。
- 与原客户端保持通信及配置兼容；用户已有端口映射继续生效。
- 端口映射仍在现有管理后台配置；服务端和管理后台的改造不在范围内。
- 内存占用是重要验收维度；选定 Rust + Tokio + Tauri 2 + Vue 3 / JavaScript，重写客户端内核。
- 桌面 UI 采用本地 `awesome-design-md` 的 `airtable` 风格，用户于 2026-10-15 确认；具体桌面适配见界面设计。

## 3. 本方案建议的产品规则

下列为待审阅建议，不冒充用户已确认的需求。界面和验收文档按这些建议展开。

| 编号 | 建议 | 目的与影响 |
|---|---|---|
| P1 | 首版保存一套连接配置，同一时刻只有一个活动连接实例 | 控制状态和资源复杂度；不引入多服务器并行连接 |
| P2 | 关闭窗口继续连接；通过托盘或菜单栏重新打开；“退出应用”才结束整个进程 | 支持长期后台运行 |
| P3 | 关闭窗口时销毁窗口及 WebView 对象，保留 Rust 宿主和内核 | 减少界面驻留开销；实际系统辅助进程释放需平台测试 |
| P4 | 登录时启动、启动后自动连接分别控制，首次默认关闭 | 启动行为可预期；首版属于用户登录会话中的应用 |
| P5 | 修改连接参数先保存，下次连接生效；用户选择“保存并重连”才中断当前连接 | 防止编辑误操作影响正在转发的数据 |
| P6 | License 和证书库密码由操作系统安全存储保管，普通配置仅保存引用；不自动上传诊断数据 | 减少本地泄露与隐私风险；属于实施前需确认的安全设计 |
| P7 | 常规日志脱敏且不记录业务载荷，日志容量有界 | 避免凭证泄露和长时间运行占满磁盘 |

首版不包含 Linux、移动端、云同步、账号体系、创建 License、端口映射管理、无人登录时的系统服务、多连接并行和自动更新服务。排除这些项目不影响当前确认的本机连接范围。

## 4. 用户流程

首次使用：安装并打开 → 手动填写连接参数或导入旧 `app.yml` → 校验服务器地址、端口、License 与证书 → 保存并连接 → 显示认证结果 → 关闭窗口，继续后台转发。

日常使用：从托盘打开 → 查看是否已连接与最近异常 → 必要时修改配置、断开或重新连接 → 关闭窗口。

异常处理：显示明确原因和可操作的下一步。网络中断显示重连倒计时；认证失败引导检查 License；证书问题展示证书验证类别；本地目标不可达显示单条转发错误，不自动误报整个客户端掉线。

管理员仍通过现有后台管理端口映射。本 App 不新增管理端流程或管理权限。

## 5. 为什么这个架构适合后台运行

网络连接、心跳、重连、日志和状态由 Rust 持有。Vue 仅在窗口打开时展示状态、提交配置和接收必要事件。窗口关闭后不依赖网页定时器维持连接。

Tauri 提供 Rust 核心进程与系统 WebView 的分离，Windows 使用 WebView2，macOS 使用 WKWebView。这为按需创建界面提供条件，但不保证某个固定的内存数值。[Tauri 进程模型](https://v2.tauri.app/concept/process-model/)

Tokio 适合使用异步任务管理连接；任务不要求逐连接创建系统线程。本项目仍须限制缓冲区、待处理任务、连接池和日志队列，语言本身不能代替资源上限。[Tokio 任务说明](https://tokio.rs/tokio/tutorial/spawning)

## 6. 需要最早解决的技术风险

1. **TLS/JKS 兼容。** 当前实现从 JKS 建立信任库，未在所读代码中显式启用主机名验证。Rust TLS 默认验证行为可能不同。先用脱敏测试证书核对证书链、主机名、算法及协议版本；不得以“忽略所有证书错误”换取兼容。
2. **UDP 行为完整。** 保留数据报边界、访客标识、目标地址、响应次数和超时语义，避免串包、端口耗尽或会话不回收。
3. **重连和停止竞态。** 手动断开必须取消重连、认证和所有相关任务，旧连接回调不得改变新连接状态。
4. **旧参数的含义。** Netty 线程参数没有一一对应的 Tokio 参数；导入时必须显示映射或不支持原因，不能静默忽略。
5. **后台内存实测。** 对比 Java 基线时必须统计 App 的完整进程树，分别测试窗口打开、关闭和持续转发。

## 7. 推荐实施顺序

先建立协议与配置兼容清单，再做 Rust 内核验证，依次打通认证、TLS、TCP、UDP、重连和停止；之后接入桌面宿主和界面，最后进行双平台打包与长期运行验证。阶段产物和完成条件见[实施计划](../06-delivery/client-app-implementation-plan.md)。

在独立目录开发新客户端，既有 Java 客户端作为行为基线继续保留。旧实现不包含可直接复用的 Rust 业务代码；可复用的是协议定义、字段语义、交互流程和测试样本。
