## 执行原则

2026-10-16 补充：用户进一步询问个位数后台内存的可行性，新增 [Rust 候选路线比较](../03-architecture/background-process-design.md#个位数内存目标的补充评估)。下面阶段是原纯 Dart 拆分方案，尚未批准或执行；先确认是否接受 Rust 常驻内核，再选择相应原型和更新实施阶段，不能将语言比较视为已经授权迁移。

先证明内存收益和进程生命周期可行，再迁移正式行为。Windows 优先，但 macOS 的 helper、沙盒与 Keychain 风险必须在早期原型中暴露。各阶段按行为测试先失败、最小实现、回归验证推进；不以模拟测试替代真实进程、系统凭证和平台打包测试。

本轮只产出架构与计划。确认进程拆分、原生宿主边界和凭证迁移方案后开始阶段 0；现有运行版保持可用。性能指标的唯一权威定义在[架构提案](../03-architecture/background-process-design.md#性能验收建议)。

## 阶段 0：验证收益与平台边界

产物：独立试验目录中的宿主 + Dart AOT 内核 + 可开关 Flutter UI 原型、原始采样和结论；不迁移真实配置，不连接真实服务器，不覆盖当前产物。

工作：

- 以当前纯 Dart 引擎连接可控本地 TCP/UDP/TLS 对端，验证离开 Flutter SDK 依赖后的编译和运行。
- 做最小 Windows 原生托盘宿主，通过继承管道启动、关闭、再次启动 UI；验证 GUI runner 不污染 IPC，重复启动只有一个内核。
- 使用合成 License 验证 Windows DPAPI 兼容读写；检查应用支持目录与旧版一致，不接触真实凭证内容。
- 采集现有版本和原型在相同场景下的完整进程树内存、CPU、句柄与恢复耗时，确认后台没有 Flutter 引擎。
- 在可用 macOS 环境进行同样的宿主/helper 启动、Keychain 合成数据、沙盒文件导入与 UI 激活试验；没有环境则明确标记未验证，不承诺 macOS 完成。

退出条件：证明 UI 确实退出且网络会话连续；给出两个常驻进程合计的真实收益和平台限制。若未达到拟定内存目标，先分析宿主、Dart 运行时和缓存占用，回报是否需要修改目标或方案，不直接进入全面改造。

## 阶段 1：提取内核与通信契约

主要范围：`lib/core/` → `packages/proxy_core/`；新增 `packages/desktop_ipc/` 和 `services/proxy_worker/`；复用现有网络行为。

先写可失败的行为测试：

- 管道分片、合并、非法长度、非法 JSON、错误版本、EOF 和发送队列上限。
- 命令重复、过期 revision、超时后查询、worker 重启后的 epoch 隔离。
- 快照与后续事件一致、日志增量缺口、无订阅不推送、慢 UI 不阻塞控制响应。
- 新进程边界下复跑官方协议向量、取消、TLS、TCP 双向及 UDP 生命周期测试。

实现 worker 单一配置所有权和引擎所有权，内置公开信任证书使用可部署资源路径。配置和凭证接口不依赖 Flutter，worker 的依赖图中不包含 Flutter 插件。

退出条件：纯 Dart 包的 analyze/test 通过；worker AOT 构建成功；可控本地对端验证通过。测试输出和构建命令写入验证记录，不修改协议以适配 IPC。

## 阶段 2：宿主、托盘与持久化

主要范围：`native/host_windows/`、`native/host_macos/`、worker 配置服务，以及原 `lib/application/storage.dart` 的职责迁移。

先写生命周期和存储故障测试：

- 并发启动、快速双击、激活旧窗口、UI 异常退出、worker 异常退出、宿主 EOF、退出时子进程卡死。
- 托盘可在无 UI 时连接/断开，认证停止不触发错误的崩溃重启，有限重启次数生效。
- 新凭证写入失败、配置替换失败、旧凭证删除失败、迁移中断和下次恢复；任何失败不得删除仍被引用的数据。
- 保留 clientId、证书内容、普通配置、凭证键；拒绝新旧版本同时写入。
- 使用合成凭证检查命令行、日志、普通文件和状态快照均不泄露秘密；系统存储不可访问时明确失败。

实现 native vault 兼容适配、单实例、私有 IPC、进程监督和原生托盘。托盘菜单和透明图标沿用用户已确认内容。迁移首选兼容原存储，仅在平台需要时使用经过测试的首启桥接。

退出条件：可以完全不启动 Flutter 而操作测试连接、查看托盘状态和退出；故障后不留下不可管理的进程；Windows 合成存储迁移测试通过。macOS 单独列出实际运行证据。

## 阶段 3：界面改为可退出的客户端

主要范围：`lib/main.dart`、`lib/application/controller.dart`、`lib/application/engine_bridge.dart`、`lib/platform/desktop.dart` 和两平台 Flutter runner。

- Riverpod 从“连接和凭证所有者”改为“IPC 状态投影与表单状态”。初始状态通过 snapshot 获取，不从 UI 另建 engine。
- 用 IPC 客户端替代 isolate bridge；`detach()` 只释放 UI 订阅，禁止复用旧 `dispose()` 的断网语义。
- 托盘移到宿主；UI 常规运行不再初始化托盘和系统 vault。保留必要的首启迁移入口，但不常驻。
- 关闭/收起先处理未保存编辑和待完成保存，成功后退出 UI；恢复时保留已保存设置、当前连接时长、待重连提示和日志入口。
- 明确区分应用退出与窗口关闭；快捷方式激活宿主，UI helper 被单独打开时转交宿主，不重复创建内核。
- 保持页面布局、透明图标、导入预览和保存后下次连接生效的行为。

验收测试：取消关闭、放弃草稿、保存失败、保存成功即关闭、UI 强制结束后网络连续、状态恢复、50 次打开/关闭以及重复激活。退出目标以进程消失验证，不能只检查窗口隐藏。

退出条件：Windows Release 实际运行验证通过，UI 操作不会意外断开隧道，后台无 Flutter 进程/模块。前台可能因为多进程而增加总占用，应记录并控制，不能仅报告后台收益。

## 阶段 4：性能、兼容性与故障验证

产物：对照测试报告、原始逐秒采样、稳定性记录、剩余限制。

- 同机器、同构建模式、同连接参数分别测量旧版和新版：未连接、空闲连接、固定 TCP/UDP 流量。记录所有应用进程总和，不复用不同场景的短样本作最终对比。
- 测量界面热恢复 P95、后台内存中位数/P95、8 小时稳定性、日志达到上限后的内存和句柄回收。
- 持续传输期间切换界面，校验数据序号/内容；分别注入 UI、worker、宿主崩溃，验证各自承诺的恢复边界。
- 真实服务端兼容测试沿用用户现有连接流程，安排会影响连接的操作前说明；不得擅自改服务器配置或使用未授权凭证。
- 静态审查子进程路径、句柄继承、IPC 超长消息、凭证出现在普通文件的风险，以及旧版数据迁移回滚。

退出条件：架构中的性能和行为验收项有实际记录；未达到项目明确标记并处理，未运行平台标记未验证。测试通过不能替代用户实际连接体验。

## 阶段 5：打包与交付

- 建立一条项目构建入口，输出匹配版本的宿主、worker 和 Flutter UI；打包脚本验证三者协议版本、资源和图标齐全。
- Windows 使用原有工具链；macOS 在对应平台编译、检查 helper 权限和应用包行为，不声称 Windows 产物能验证 macOS。
- 干净用户目录进行首次启动、保存、连接、收起、恢复、退出检查；使用合成旧数据进行升级和回滚演练。
- 更新 README、架构、验证记录、启动方式和故障定位说明；批准且实施后再替换 AGENTS 中当前 isolate 架构约定，保留提案追溯链接。
- 本地交付新的可运行产物。提交、推送、tag 和正式发布按用户后续明确授权执行。

退出条件：发布目录单独即可运行，不需要开发机 SDK；应用退出没有残留进程；旧版配置可恢复；提供真实内存对照和平台验证范围。

## 回滚边界

在独立构建目录保留原版产物。切换版本前完整退出该客户端自己的进程；任何时刻只有一套程序持有配置写锁。普通配置保持现有 schema 和语义，凭证优先保持存储兼容。

如果必须迁移存储，不覆盖唯一旧副本，先验证可读和恢复路径再切换标记。迁移之后用户新保存的数据不能被旧备份静默覆盖；回滚前验证旧程序是否能读取最新数据，必要时先进行明确的兼容导出。不得为回滚落地明文 License。

## 尚待确认的架构决策

首先确认是否坚持纯 Dart 内核，或为了个位数目标接受 Rust 内核。保持 Dart 时采用“三部分、后台两个常驻进程”的原提案；接受 Rust 时先验证“原生托盘与 Rust 内核同进程”的收益，再更新本计划。两种路线均关闭/收起时退出 Flutter UI，均先测量再迁移。当前没有实施完成项。
