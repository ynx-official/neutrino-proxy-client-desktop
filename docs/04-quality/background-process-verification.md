## 发现并修复的问题

1. IPC 的 async* 解码器在宿主静默时，取消订阅可能等待下一帧，导致 UI 退出停滞。真实流回归测试先超时失败，改为同步 Transformer 后通过，detach 不发送 disconnect/shutdown。
2. 旧 `ConnectionScope.wait` 为每次 UDP 地址查找向同一个未完成的 done Future 注册监听；已完成操作仍被保留到整条连接结束。长时间传输样本出现内存上涨后定位；计数回归明确复现 10,000 个操作后仍保留 10,000 个注册。改为可移除的取消注册，操作完成/失败立即移除，关闭时仍取消未完成操作且处理迟到错误。该修复不修改代理帧或重连规则。
3. UI 请求先等待管道写完才监听响应，可能在写入受阻且宿主退出时产生未处理错误并拖延失败反馈。新增阻塞写端的回归先失败后通过；现在同时观察写入和响应，关闭 UI 还有超时退出边界。

## 真实窗口验证范围

隔离测试配置使用本地 TLS 服务、合成 License、一个 TCP 和一个 UDP 回显目标。已完成 2 次 UI 启动：一次正常关闭、一次强制结束。worker PID 不变、认证次数保持 1、TCP/UDP 序号和载荷正确，重新启动 UI 能 attach；结束应用后两个后台进程退出。初步前台三个进程合计约 72.6 MiB 私有工作集。

随后 50 次可见窗口循环被用户手动中断，不计为通过。此后测试改为 `--cycles 0`，不再弹窗。34 项测试包括现有未保存表单确认，但不能替代 50 次完整原生窗口循环。恢复耗时只有两个初步样本（2.35/1.85 秒），不声称恢复 P95 达标。

## 内存口径与当前样本

Windows x64 Release；MiB = 1024² 字节。统计一次被测应用的完整进程树，后台包括 native host 和 Dart worker。使用 QueryWorkingSet 的非共享页计算私有工作集，同时记录总工作集和私有提交量。测试服务端与采样器不属于客户端进程树。未裁剪工作集、未定时强制 GC。

旧版基线是本机此前 5 个未连接样本、约 23 秒，中位数 63.93 MiB；它是历史短样本，不是重新跑的同负载 A/B 长测。以下新版测量分场景列出，不能用未连接数字代表持续传输上限。

| 场景 | 样本及私有工作集 | 状态 |
| --- | --- | --- |
| 旧 Flutter 单进程隐藏、未连接 | 5 样本，中位数 63.93 MiB | 历史基线 |
| 新版后台未连接 | 60 样本，中位数 6.375 / P95 6.438 MiB | 最终内核代码 |
| 新版 TLS 连接、无业务流量 | 120 样本，中位数 8.491 / P95 9.527 MiB | 最终内核代码，1 秒心跳 |
| 新版 TLS + TCP/UDP 持续回显 | 600 样本、613.6 秒，中位数 12.754 / P95 13.500 / 峰值 13.863 MiB | 每流发送间隔 10 ms；修复后 AOT 内核 |

新版未连接短样本较旧版未连接历史中位数减少约 90.0%。TLS 空闲仅采样约 2 分钟：支持该条件下个位数，不能承诺长时间或任意流量均小于 10 MiB。

| 新版场景 | 总工作集中位数 | 私有提交量中位数 |
| --- | ---: | ---: |
| 未连接 | 29.379 MiB | 10.875 MiB |
| TLS 空闲 | 32.935 MiB | 14.582 MiB |
| TLS 持续转发 | 37.344 MiB | 23.152 MiB |

修复后高频测试完成 55,077 个 TCP 回显和 54,529 个 UDP 回显，每帧 1,028 字节，全部验证序号和载荷；认证次数保持 1，没有意外断开。首/末各 60 个样本私有工作集中位数为 11.377 / 13.265 MiB。此短测不等同于 8 小时稳定性证明。

用于发现问题的修复前样本持续 1,847.1 秒、1,800 个样本：首/末 60 个样本从 11.027 增至 27.145 MiB，峰值 27.727 MiB。当时每流发送间隔 100 ms、累计约 18,000 次回显；该组作为故障依据保留，不能混入最终性能结论。修复后发送频率更高，累计流量也更多，但测量时长不同，不作为严格同负载长期 A/B 测试。

所有逐样本数据见 [CSV](results/windows-background-2026-10-16.csv)，`discovery-before-fix` 与 `final-*` 明确区分。短样本未按原提案预热 5 分钟；启动/GC 预热会影响分位数。性能采样 worker 与最终 worker 使用同一取消机制；其后最后的 UI 失败处理和托盘文案调整另经最终 Release 构建及故障测试验证。
